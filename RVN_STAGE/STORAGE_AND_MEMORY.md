# Размещение памяти и данных RVN

Проверенная машина: 32 ГиБ RAM, RTX 4070 с 12282 МиБ VRAM,
NVMe HP SSD FX900 Pro на C: и SATA HDD WD60EZAZ на K:.
Во время проверки свободно примерно 241 ГБ на C: и 2,22 ТБ на K:.
Предложенная схема подходит; скорость на полной RVN-цепочке ещё не измерялась.

| Уровень | Данные | Реализация / ограничение |
|---|---|---|
| GPU VRAM | Активный KawPoW DAG, вычисления, рабочие буферы | CUDA-воркер строит DAG и ищет nonce на GPU; проверены векторы Core на RTX 4070; сетевые задания ещё не подключены |
| RAM / Java heap | P2P, шаблоны, задания, mempool, light-cache, горячие объекты | Профили RVN: heap до 4 ГиБ; P2P уже ограничен по числу/байтам сообщений; полноценные RVN mempool/jobs ещё предстоит подключить |
| RAM / native RocksDB | Кэш таблиц, индексов/фильтров, memtable | 64 МиБ кэш заголовков + 256 МиБ кэш монет; до 128 МиБ memtable суммарно, отдельно от heap |
| C:\RVNJavaNjde | RocksDB заголовков/индексов и монет/chainstate; временные файлы | SSD хранит маленькие ссылки на блоки/undo, сами новые payload туда не попадают |
| K:\RVNJavaNjde | Полные блоки, undo, архивы, логи | Последовательные сегменты blocks/undo по 128 МиБ, контрольные суммы и синхронный сброс перед публикацией ссылки |

RocksDB использует память вне Java heap. Лимиты кэшей и memtable не являются
абсолютным лимитом всего native-процесса: остаются служебные структуры, фоновые
компактации и файловый кэш Windows. В профилях также ограничены Java direct
buffers до 512 МиБ; это ограничение не распространяется на RocksDB JNI.
Не следует отдавать JVM всю RAM и оставлять ОС без файлового кэша.
[RocksDB: memory usage](https://github.com/facebook/rocksdb/wiki/Memory-usage-in-RocksDB).

## DAG и VRAM

Размер берётся из реального расписания KawPoW, с epoch = height / 7500 и
prime-adjusted размером набора. `RvnKawpowGpuMemoryPlan` проверяет именно
свободную память GPU с отдельным резервом, а не только паспортный объём карты.
При нехватке места `requireFits()` отказывает в допуске; подкачка DAG через RAM
или HDD в цикле хеширования не предусмотрена. CUDA-воркер дополнительно проверяет
реальную свободную VRAM перед выделением DAG, временного light-cache и буферов.
Временная GPU-копия light-cache освобождается после построения DAG.

Пример, **не текущая высота сети**: на высоте 5 000 000 DAG занимает около
6,2 ГиБ. Один такой DAG с резервом помещается в 12 ГиБ; два целиком — уже нет.
Поэтому базовая политика — один активный DAG, смена epoch без удержания двух
полных наборов. Light-cache остаётся в RAM, CPU-верификатор уже удерживает
только одну epoch. Полную копию GPU DAG в heap держать не требуется.
Каталог `dag` на K: зарезервирован для будущих снимков/повторного использования;
персистентный DAG-кэш сейчас не реализован.

## Запись на разные диски и восстановление

1. Блок или undo добавляется в конец HDD-сегмента вместе с размером и SHA256d.
2. `FileChannel.force(true)` завершается **до** записи ссылки в индекс.
3. Ссылка, метаданные и указатель прогресса фиксируются синхронным WriteBatch
   RocksDB. Для монет тот же batch атомарно меняет UTXO и вершину.

Если процесс падает между пунктами 2 и 3, остаются лишние неиндексированные
байты, а прежнее состояние монет остаётся целым. Если фиксация состоялась,
ссылка ведёт на предварительно сброшенную запись. При чтении проверяются
границы, заголовок и checksum; потеря/подмена файла не превращается в пустой undo.
Откат удаляет ссылку из DB, но не вырезает байты из середины сегмента.
GC/pruning осиротевших данных пока не реализован; сегменты нельзя удалять вручную.

Такой порядок сохраняет атомарность индекса без общей транзакции двух дисков
и выводит крупные тела из LSM-компактаций. Однако синхронный сброс HDD остаётся
ограничением IBD/реорганизаций; здесь не заявляется измеренное ускорение.
[RocksDB: tuning guide](https://github.com/facebook/rocksdb/wiki/RocksDB-Tuning-Guide).

## Пути и совместимость

```yaml
ravencoin:
  data-directory: '${RVN_DATA_DIRECTORY:K:/RVNJavaNjde}'
  storage:
    hot-directory: '${RVN_HOT_DIRECTORY:C:/RVNJavaNjde}'
```

- C:\RVNJavaNjde\headers — заголовки, индексы блоков и ссылки на тела.
- C:\RVNJavaNjde\coins — монеты, вершина, ссылки на undo.
- C:\RVNJavaNjde\tmp — временные файлы JVM в RVN-профилях IntelliJ.
- K:\RVNJavaNjde\blocks и \undo — независимые последовательные архивы.
- K:\RVNJavaNjde\archives — архивы и heap dumps; \logs — логи с ротацией.

Ни DB, ни архивы автоматически не переносятся и не сбрасываются. Если найдена
старая DB на K:, а новая на C: отсутствует, приложение откажется незаметно
начинать пустую цепочку. Нужна остановленная нода и отдельная миграция; временно
можно явно установить RVN_HOT_DIRECTORY на старый корень. Старые API хранилищ
поддерживают встроенные тела/undo для совместимости, новые Spring-конфигурации
пишут payload в HDD-сегменты. DB с внешними ссылками нельзя открыть без архива.
Старые встроенные записи не переписываются автоматически.

## Проверки и оставшаяся работа

Тесты покрывают ссылки вместо payload в RocksDB, ротацию сегментов, чтение
после перезапуска, checksum/размеры, откат и child-JVM `Runtime.halt` до/после
фиксации индекса. Проверка реальных дисков в изолированных каталогах C:\...\tmp
и K:\...\archives подтвердила запись, перезапуск и undo. Это проверка процесса,
не испытание отключением питания и не benchmark производительности.

Распределение хранения подключено к существующей ноде. Оно не завершает майнер:
по-прежнему нужны полный assets consensus и подключение его изменений к хранилищу,
проверенные шаблоны/приём кандидатов и подключение CUDA-воркера к заданиям. Native replay всё ещё
останавливается перед assets. Это ограничение не снято ради запуска.

Метаданные assets теперь поддерживаются в той же RocksDB на C:, что и UTXO.
Один синхронный WriteBatch фиксирует обе группы изменений, общий undo и tip;
undo предварительно сохраняется в HDD-архив. Проверяются исходные значения,
перезапуск и совместный откат. При первой записи assets версия схемы меняется
атомарно: старая нода с поддержкой только native coins откажется открыть DB.
Это API хранения; текущий native replay ещё не формирует изменения assets.
