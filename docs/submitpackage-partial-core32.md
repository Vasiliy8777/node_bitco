# Частичный submitpackage и комиссии новых транзакций

Эталон: Bitcoin Core 32.1 `MemPoolAccept::AcceptPackage`, `AcceptSubPackage`,
проверки `m_client_maxfeerate` и RPC `submitpackage`. Копии исходников:
`target/core-update-audit/btc-validation32.cpp` и
`target/core-update-audit/core32-rpc-mempool-reference.cpp`.

RPC использует отдельный путь submission вместо предварительной проверки
всего пакета с последующим атомарным добавлением:

- Каждая неизвестная транзакция сначала проверяется и принимается отдельно.
  Успешные родители сохраняются при отказе ребёнка. После окончательного
  отказа одной транзакции остальные всё равно проверяются индивидуально.
- Известные txid сохраняют принятый witness и не проходят повторный client cap.
- При отсутствии окончательных отказов транзакции, отклонённые по комиссии,
  отсутствующим входам или пересматриваемым RBF/capacity-условиям, повторно
  оцениваются оставшимся пакетом. Комиссии уже принятых родителей исключены.
- Ответ содержит `package_msg` и отдельный результат каждого wtxid. Ошибки
  транзакций возвращаются в `error`, а не превращают весь вызов в RPC -26.
- Новые записи получают `effective-feerate` и `effective-includes`: собственный
  wtxid при индивидуальном приёме, оставшийся набор при CPFP. Известные записи
  возвращают только base fee; иной witness возвращает `other-wtxid`.
- `maxfeerate` применяется к новой транзакции внутри admission до её скриптов.
  Сравнивается усечённый modified-feerate Core; промежуточное умножение не
  переполняет long. Отказ ребёнка по cap сохраняет уже принятого родителя.
- `maxburnamount` проверяется по каждому выходу при декодировании, включая
  невалидные операции script. Проверка происходит до следующего rawtx и до
  побочных эффектов приёма. RPC проверяет child-with-independent-parents.

`NodeValidationService` сохраняет изменения частичного приёма и уведомляет
майнинг; relay объявляет только записи, оставшиеся в mempool, используя
реально принятый witness. Обычный атомарный `admitPackage` остаётся доступен
для внутренних операций, которым требуется именно атомарный приём.

Проверки `PartialPackageSubmissionTest` покрывают сохранение родителя,
CPFP-метаданные, известные записи, cap, продолжение проверки независимых
родителей и границу усечения CFeeRate. `MiningRpcTest` проверяет передачу cap
и сериализацию частичного результата без прежнего preflight. Независимый
`BitcoinCore32CompatibilityTest` сравнивает полные ответы и состав пула при
плохой подписи ребёнка, повторной подаче, исправлении witness, повторной
подаче известного пакета с tiny cap, CPFP и cap только нового ребёнка.
Дополнительно сравниваются ранние RPC-отказы topology/burn.

Общая фаза реального CPFP-приёма добавлена следующим изменением:
[порядок проверок и пределы](shared-submission-phase-core32.md).
Оставшийся объём: полная типизация consensus/policy/RBF-отказов и их debug
сообщений, оставшиеся индивидуальные TRUC/client cap/RBF приоритеты,
eviction/пересечение замен в сложных пакетах и матрица
клиентских лимитов с fee deltas/TRUC/ephemeral. Новый путь не закрывает
бюджетный оптимизатор, постоянный TxGraph и равные ставки.
