# Актуализация плана после интеграции BIP152

База проверки: commit `840faf4`. Рабочее дерево перед проверкой чистое.
Проверены изменения после `5b030ea`, связанные реализации и тесты; это целевая
проверка изменений, а не повторная сертификация всего консенсуса.

## Что уже сделано

- Лимиты и ротация transaction announcements, кэш статусов предков и постоянный
  индекс кандидатов по chainwork сохранены.
- В NodeRelayService есть оценочные лимиты исходящих задач: 16 МБ на пира,
  64 МБ глобально; учтены выполняющиеся задачи и освобождение отменённых задач.
  Это не лимит полной heap-памяти и не общий writer всех P2P-компонентов.
- BIP130: sendheaders, учёт известного заголовка пира, связные объявления headers
  с fallback на inv; добавлен NodeRelaySendHeadersTest.
- BIP152: SipHash, codecs, согласование v2, reconstruction через mempool,
  getblocktxn/blocktxn, ограничения глубины выдачи и timeout fallback.
  Добавлен NodeRelayCompactBlockTest. Эти механизмы больше не следует перечислять
  как полностью отсутствующие; полнота и отказоустойчивость требуют проверки.
- Изменение HeaderSyncCoordinatorTest в последних коммитах учитывает sendcmpct
  в handshake. После этой проверки рабочий путь NodeLifecycleService переведён
  на пакетный API HeaderSyncCoordinator без накопления allProcessed за всю историю.

## Исправлено в этой доработке

Декодеры cmpctblock, blocktxn и getblocktxn выделяли ArrayList по объявленному
числу элементов, ограничивая его только Integer.MAX_VALUE. Короткий пакет с большим
счётчиком мог запросить огромную аллокацию до обнаружения отсутствующих данных.
Теперь до выделения массива счётчик сверяется с оставшимися байтами: минимум
11 байт на prefilled entry, 10 на transaction envelope, 1 на differential index.
Это проверки достаточности wire-данных, не новые правила консенсуса.
Добавлены проверки больших счётчиков в коротких пакетах и roundtrip blocktxn v1/v2.

Формат сверялся с [BIP152](https://github.com/bitcoin/bips/blob/master/bip-0152.mediawiki).

## Приоритет дальнейшей работы

1. Для сохранённых Partial добавлены отдельные оценочные бюджеты 16 МБ на пира и
   64 МБ глобально, дополнительно к пределу 16 блоков на пира. Учитываются списки
   и удерживаемые транзакции, включая ссылки на транзакции mempool. Это консервативные
   единицы учёта, не измерение heap; временные аллокации декодирования и reconstruction
   ими не ограничиваются. При отказе квоты запрашивается полный witness block;
   существующие запросы не вытесняются. Повторный хеш не заменяет Partial и не продлевает
   TTL. Ответ, timeout, disconnect и shutdown освобождают сохранённые квоты.
   Повторяющиеся short IDs теперь оставляют все неоднозначные позиции незаполненными;
   ошибка BlockValidationException при полном/частичном восстановлении запускает
   запрос полного блока. Ошибки хранения/runtime не маскируются как коллизии.
   Ответы block на такие запросы обрабатываются отдельным bounded-реестром (16 на пира,
   256 глобально, 30 секунд). Дубликаты подавляются; ответ, notfound, timeout, disconnect
   и shutdown очищают запрос. Полный блок проходит обычную валидацию без повторного
   reconstruction fallback. Если тот же блок уже ожидает bulk downloader, dispatcher
   отдаёт его тому пути, а запись fallback позже истекает.
   Далее проверить CPU и временную память до сохранения Partial, стресс-нагрузку на
   fallback-лимиты и переключение источника после timeout/notfound (сейчас запрос
   только снимается; повторную загрузку может инициировать основной sync).
2. GETDATA теперь обслуживается порциями до 128 элементов и не более одного блока
   за шаг. Продолжение возвращается в хвост очереди того же пира с сохранением квоты
   всего запроса; поставленные объявления свежих блоков проходят между порциями.
   Это справедливое чередование FIFO, а не отдельная очередь строгого приоритета.
   NOTFOUND собирается для всего запроса; для block-only запросов mempool не читается.
   Остаются оптимизация поиска транзакций (сейчас снимок mempool на каждую порцию),
   тесты глобальных/per-peer квот, освобождения
   при shutdown и насыщения очереди. Проверить оценку памяти getblocktxn indexes.
   Heartbeat больше не отправляет ping последовательно в потоке обхода: отдельные
   задачи ограничены одной на пира и 256 на сервис, без очереди. Зависшая запись
   приводит к закрытию соединения после 10 секунд (либо меньшего ping timeout),
   проверка выполняется с периодом heartbeat. При заполнении лимита новые задачи
   ждут следующего обхода. Shutdown закрывает соединения с незавершённой записью.
   pingLock больше не удерживается во время I/O; nonce публикуется до отправки,
   чтобы быстрый pong не терялся. Используются ограниченные platform threads,
   чтобы synchronized socket I/O не занимал carriers виртуальных потоков Java 21.
   Дополнительно все записи через PeerConnection.send получили общий transport
   deadline: по умолчанию 10 секунд вместе с ожиданием sendLock. ReentrantLock
   допускает ограниченное ожидание и прерывание с сохранением interrupt flag.
   Таймер закрывает конкретный сокет без захвата sendLock; успешная запись отменяет
   таймер, отменённая задача удаляется из очереди. На соединение активен не более
   одного таймера записи. Это локальная политика, не правило консенсуса.
   Все send теперь резервируют транспортную квоту до ожидания канала и кодирования:
   64 незавершённые записи / 16 МиБ на соединение и 1024 записи / 64 МиБ на процесс.
   Бюджет общий для экземпляров PeerConnection, учитывает ожидающие и активные send;
   оценка на сообщение — 256 + 3 * payloadLength (удерживаемый payload и копии encoder).
   Исчерпание возвращает IOException до записи сообщения; квота освобождается при
   успехе, ошибке, прерывании и выходе по timeout. Close не сбрасывает счётчики раньше
   выхода отправителей. Это отдельные от NodeRelayService единицы учёта, не точный
   предел heap и не защита аллокаций до вызова send. Transport сам не отключает пира
   за исчерпание квоты; ошибку обрабатывает вызывающий компонент.
   Для pong и ответов getaddr (addr/addrv2) добавлен sendAsync: один отправитель
   на соединение, FIFO-очередь до 63 ожидающих задач, общие квоты с синхронным send.
   Рабочий поток создаётся по потребности и завершается после 5 секунд простоя.
   Deadline включает очередь, ожидание sendLock и запись. Ошибка выполнения через
   Peer передаётся в handleReaderFailure; close снимает очередь и освобождает квоты,
   активная задача освобождает резерв при выходе. FIFO относится к sendAsync;
   общего порядка с конкурентными синхронными send этот API не обещает.
   Handshake и остальные вызовы send пока синхронны. Объединение остальных путей
   отправки и стресс-проверка насыщения heartbeat остаются задачами. Кодирование
   адресного ответа до sendAsync и обработка входящих addr всё ещё идут на reader.
   Для addr/addrv2 добавлен общий per-peer token bucket: начальный burst 1000 адресов
   и 10 сообщений, восстановление по 1 адресу и 1 сообщению в секунду. Message budget
   проверяется до декодирования, address budget — до преобразования/записи в AddrMan;
   превышение молча отбрасывается, без disconnect. Неподдерживаемые/непригодные адреса
   также расходуют квоту, чтобы поток таких записей не обходил ограничение CPU.
   Это локальная политика ресурсов, не правило консенсуса и не заявление о точном
   совпадении политики Core. Weak-key учёт не удерживает отключённые Peer после GC.
   Декодирование допустимых сообщений и обработка адресов всё ещё идут на reader;
   отдельная ограниченная рабочая очередь и общий бюджет всех пиров остаются задачами.
3. Накопление HeaderSyncCoordinator.allProcessed устранено в рабочем lifecycle:
   пакеты передаются обработчику после валидации и сохранения, до следующей загрузки;
   возвращается long-счётчик. Сохранён старый collecting API для совместимости — он
   по-прежнему расходует память пропорционально результату, и для полной истории
   использовать его не следует. Проверки прогресса и курсор последней обработанной
   ветки сохранены. Для activeBlockDepth, bestActiveLocator, headers/findBlock и
   проверки activeHeadersAfter добавлен общий кэш предков до 65536 индексов:
   поиск начинается с ближайшей сохранённой высоты не ниже требуемой. При любом
   изменении tip кэш целиком сбрасывается, включая reorg на той же высоте и откат.
   Headers строятся в прямом порядке только для возвращаемого окна до 2000 заголовков.
   Первый холодный запрос и запрос после смены tip всё ещё могут потребовать O(H)
   чтений. Постоянный индекс активной цепи по высоте и более точная инвалидизация
   остаются возможной следующей оптимизацией. Замер heap при mainnet replay ещё
   не проводился; это не подтверждение общей производительности mainnet.
4. Провести сетевые испытания Core A → Java → Core B с BIP130/BIP152, fallback,
   reconnect/reorg и фактическим принятием блока. Unit-тестов negotiation недостаточно.
5. Полный mainnet replay с проверкой UTXO/chainwork и активаций, аварийное восстановление
   и длительная работа ASIC остаются неподтверждёнными. Политики mempool рассматривать
   отдельно от консенсуса; прежняя задача совместимости политик не закрыта.

sendAsync. Handshake сохраняет синхронную отправку. Новые сценарии проверяют
возврат при заблокированном writer, FIFO трёх ответов, общий с send отказ по квоте,

PeerAddressProtocolTest — 10. Отменённые при close ожидающие задачи освобождают
квоты без callback: владелец уже закрывает соединение.
Полный прогон app/target/async-response-tests.log: 3524 теста, 3 skipped,
0 failures/errors, exit code 0. HeaderSyncCoordinatorTest: 3 успешных;
Core mining roundtrip в regtest выполнен за 9.075 с.

нагрузки по-прежнему необходимы для оценки готовности майнинговой полной ноды.
