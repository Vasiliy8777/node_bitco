# Скорость синхронизации блоков — 1 октября 2026

> Historical report: the 32/128-request settings below have been superseded.
> Current production policy uses at most 16 requests per peer. See
> [the October 6 Core policy comparison](ibd-core-policy-20261006.md).


## Исправление

`SchedulerBlockDownloadSession` хранил все `DownloadState` до закрытия сессии.
Выбор следующего запроса каждый раз перебирал список с начала, включая завершённые
запросы. Поиск владельца хеша и принятие блока от альтернативного транспорта тоже
перебирали историю. Сессия охватывает несколько частей цепочки по 32768 заголовков,
поэтому её стоимость не ограничивалась размером текущего окна загрузки.

Теперь `LinkedHashMap<Hash256, DownloadState>` содержит только незавершённые запросы.
Завершение обычной или альтернативной загрузки сразу удаляет запись. Порядок выдачи
незавершённой работы сохранён, поиск по хешу выполняется непосредственно в карте.
`submittedHashes` сохраняется на время сессии: повторная подача запроса по-прежнему
отклоняется, поздние дубликаты не попадают в независимый путь валидации. Этот набор
по-прежнему растёт с количеством загруженных блоков; изменение не делает всю сессию
константной по памяти. Очередь результатов сохраняет собственный счётчик pending:
блок, принятый альтернативным транспортом, учитывается до получения результата.

## Измерения

Windows, JDK 21, RocksDB, отдельные временные базы. Скорость вычисляется только для
указанного участка; подготовка тестовой цепочки не включена. В тестах нет порога
времени, зависящего от машины. Это синтетическая regtest-цепочка с coinbase, а не
проверка производительности на современных блоках mainnet.

| Сценарий | Блоков | До | После |
| --- | ---: | ---: | ---: |
| Loopback P2P, scheduler + валидация + RocksDB, без debugger/JFR | 131072 | 61,377 с / 2135,5 блоков/с | 38,024 с / 3447,1 блоков/с |
| Короткий loopback P2P с JFR profile | 32768 | 6,617 с / 4952,0 блоков/с | 6,619 с / 4950,5 блоков/с |

Повторный запуск исправленного кода дал 34,483 с / 3801,1 блоков/с.
На длинной цепочке получено около 1,61–1,78 раза по средней скорости; на короткой
заметного выигрыша нет. Сравнение проведено с исходной реализацией планировщика
при одинаковом тесте; после контрольного запуска исходника оптимизированный файл
восстановлен.

Дополнительные измерения:

- Локальное подключение 4096 блоков пакетами по 512 без сети: 0,666 с,
  6153,5 блоков/с (исходная реализация).
- Полная нода с настоящим изолированным Bitcoin Core peer: 8192 блока за 2,439 с,
  3358,1 блоков/с. Здесь в интервал включены запуск lifecycle, handshake и загрузка
  заголовков. Core заранее генерирует блоки; это скорость Java-ноды, **не** Core IBD.
- JFR исходного loopback-запуска показывает `findAssignableState` в 35 CPU samples.
  Отладчик подтвердил 4096 сохранённых состояний после результата с индексом 4000
  при 95 оставшихся запросах. Отладочный запуск не использован для измерения скорости.

Наблюдавшиеся пользователем 200 блоков/с на удалённых пирах локально не воспроизведены.
Эти измерения не обещают 800–1000 блоков/с на любой сети: требуются сопоставимые
высота, содержимое блоков, задержки пиров, диск и настройки запущенной ноды.

## Воспроизведение

Из корня репозитория, PowerShell:

```powershell
# Длинная загрузка через настоящее P2P framing и планировщик, без внешней сети.
.\mvnw.cmd -o -pl app -am test '-Dtest=BlockSyncCoordinatorTest#measuresStreamingInitialSync' '-Dsurefire.failIfNoSpecifiedTests=false' '-Dibd.benchmark.blocks=131072'

# Только подключение уже подготовленных блоков; проверяет также открытие базы повторно.
.\mvnw.cmd -o -pl app -am test '-Dtest=InitialSyncThroughputTest' '-Dsurefire.failIfNoSpecifiedTests=false' '-Dibd.benchmark.blocks=4096' '-Dibd.benchmark.batch=512'

# Полная нода и изолированный локальный Core; тест по умолчанию выключен.
.\mvnw.cmd -o -pl app -am test '-Dtest=BitcoinCoreMiningRoundTripTest#measuresInitialSyncFromCore' '-Dsurefire.failIfNoSpecifiedTests=false' '-Dibd.benchmark.core=true' '-Dbitcoin.core.binary=C:/Program Files/Bitcoin/daemon/bitcoind.exe'
```

Локальные журналы и профили этой проверки сохранены в `target/ibd-performance/`;
это временные артефакты, они не входят в исходный код и удаляются при `mvn clean`.

## Удалённые пиры: ограничение задержкой сети

После уточнения о testnet добавлен тест с независимой задержкой каждого ответа
на 150 мс. В отличие от последовательного sleep на каждый блок, он позволяет
запросам находиться в полёте одновременно и моделирует ограничение окна по RTT.
Один пир, небольшие coinbase-блоки, реальный TCP/framing/scheduler/validation/RocksDB:

| Запросов на пир | Блоков | Время | Скорость |
| ---: | ---: | ---: | ---: |
| 32 | 2048 | 10,141 с | 202,0 блока/с |
| 128 | 2048 | 2,621 с | 781,3 блока/с |
| 32 | 8192 | 40,468 с | 202,4 блока/с |
| 128 | 8192 | 10,201 с | 803,1 блока/с |

В этом сценарии прежний предел объясняется размером окна: 32 / 0,15 ≈ 213
блоков/с до накладных расходов. Это воспроизведение механизма ограничения,
а не измерение RTT или количества фактически отдающих блоки пиров пользователя.

Профиль `testnet` теперь задаёт:

```yaml
bitcoin:
  p2p:
    max-blocks-in-flight-per-peer: 128
```

`NodeConfiguration` передаёт настройку планировщику. Допустимы значения 1–256;
без настройки остаётся прежнее значение 32. Для всей download-сессии введён
общий предел **256 активных запросов**, разделяемый всеми пирами. Увеличение
окна одного пира поэтому не превращается в 128 запросов на каждого из десяти
пиров одновременно. Это предел запросов, а не байтов: крупные блоки требуют
больше памяти. Общий лимит при большом числе пиров может ограничить суммарную
скорость, зато ограничивает число одновременно запрошенных блоков.

Настройка применяется после перезапуска с профилем `testnet`; пересоздавать базу
не требуется. Другие профили автоматически не получают значение 128.

Повторить измерение, затем заменить последнее значение 32 на 128:

```powershell
.\mvnw.cmd -o -pl app -am test '-Dtest=BlockSyncCoordinatorTest#measuresStreamingInitialSync' '-Dsurefire.failIfNoSpecifiedTests=false' '-Dibd.benchmark.blocks=8192' '-Dibd.benchmark.rttMillis=150' '-Dibd.benchmark.perPeer=32'
```

Тесты дополнительно проверяют глубокое окно одного пира, общий предел для трёх
пиров, отсутствие голодания пиров, выдачу ровно одного нового запроса после одного
завершения, отклонение недопустимых значений и загрузку настройки из testnet YAML.
Фактическая скорость на удалённой testnet зависит также от числа подходящих пиров,
их задержек, доступности истории, пропускной способности и содержимого блоков.

Регрессионный прогон после настройки окна: 115 тестов, failures/errors — 0, пропущено 1. BUILD SUCCESS. Включены планировщик, лимиты in-flight, таймауты, stall, reconnect, relay, NodeConfiguration, полный BlockSyncCoordinatorTest и локальная интеграция с Core. Журнал: `target/ibd-performance/latency-regressions.log`.

## Исправление пауз после введения общего лимита

После сообщения о чередовании скорости с нулём воспроизведена ошибка приоритета
при заполненных 256 слотах. `retryBlock` освобождал слот для раннего зависшего
блока, но `assignAvailable` сначала выбирал пира. Если очередь round-robin
указывала на прежнего владельца, которому повтор этого блока запрещён, слот
занимал более поздний блок. Повторный запрос раннего блока оставался без пира,
несмотря на наличие другого подходящего пира со свободным персональным окном.

Регрессионный тест с тремя пирами и заполненным общим лимитом на прежнем коде
падает с `Later work consumed the frontier rescue slot`. Исправленный планировщик
сначала выбирает самый ранний незавершённый запрос, который может обслужить
доступный пир, затем выбирает пира в порядке round-robin. Полностью занятые пиры
отфильтровываются до обхода запросов. Если ранний запрос сейчас никто не может
обслужить, полезная загрузка более поздних блоков продолжается.

Лимиты не увеличивались. Индикатор BLK по-прежнему показывает фактическую скорость
за интервал; нулевые интервалы не маскируются сглаживанием. Для диагностики реальных
удалённых соединений раз в пять секунд появляется строка `IBD pipeline`:

- `intervalMs`: длительность интервала; `received`/`processed`: количество
  полученных/обработанных блоков за этот интервал, не скорость в секунду;
- `buffered`: полученные тела, ещё ожидающие обработки; `pending`: запросы,
  результаты которых сессия ещё не выдала;
- `connectBatchMs`: суммарное время в `processInitialSyncBatch` за интервал;
- `frontierHeight`, `frontierAvailable`, `frontierPeer`: следующий блок, наличие
  его тела в буфере и владелец активного запроса либо `UNASSIGNED`.

Получение блоков при отсутствии обработки указывает на необходимость проверить
ранний блок и его владельца. Малое получение при пустом буфере требует проверки
сети/пиров. Большое `connectBatchMs` выделяет стоимость валидации/записи состояния.
Сам факт нулевой секундной скорости не доказывает конкретную причину; журнал
удалённой testnet после изменения ещё нужен для проверки оставшихся пауз.

Проверка исправления приоритета: 112 выбранных тестов планировщика, reconnect,
таймаутов, relay, конфигурации и BlockSyncCoordinator — успешно, без пропусков.
После добавления диагностики повторены 14 тестов планировщика и сетевой benchmark:
8192 блока, RTT 150 мс, окно 128 — 10,264 с / 798,2 блока/с. Диагностические строки
получены в этом запуске; это всё ещё искусственный RTT, а не измерение удалённой сети.
