# Аудит готовности Bitcoin-ноды — 23 сентября 2026

## Вывод

Эксперименты с solo-майнингом в regtest допустимы, но текущий end-to-end тест
публикации блока в Core не проходит; считать даже этот путь подтверждённым сейчас нельзя.
Считать проект полностью
совместимым с Bitcoin Core и использовать его как единственный источник работы для
реального mainnet-майнинга пока не следует. Полная совместимость консенсуса не доказана;
по политикам и P2P найдены конкретные различия и незавершённые механизмы.

Проверка включает чтение реализаций, конфигурации и тестов, сопоставление с исходниками
Core v31.1 и release notes 31.0, запуск Maven и изолированного Core regtest.
Это не формальная верификация, полный mainnet replay, сетевой pentest или тест ASIC.
В рамках аудита рабочая сеть и пользовательские процессы не изменялись.

## Что уже реализовано

- Консенсусный путь подключения: PoW/retarget, chainwork, MTP, версии блоков,
  BIP34/30, UTXO, суммы и maturity coinbase, finality/sequence locks, Script,
  SegWit, Taproot, witness commitment, weight/sigops и реорганизации.
- Внешние векторы Core v30: 1212 Script, 213 transaction, 500 legacy sighash;
  дополнительно BIP340/341, небольшие реальные цепи и regtest-сравнения с Core.
  Векторы Script проверяют принятие/отказ, а не идентичность всех кодов ошибок.
- Mempool: standardness, RBF, зависимости, TRUC, локальный package admission,
  вытеснение/expiry и восстановление после reorg.
- P2P: outbound, reconnect/backoff, AddrMan NEW/TRIED, test-before-evict feeler,
  входящий BitcoinServer с лимитом соединений, DNS discovery, addr/addrv2/getaddr,
  version/verack, wtxidrelay, ответы pong, загрузка headers/blocks и live sync.
- Mining: контекстно проверяемый шаблон, coinbase/commitment, RPC GBT/submitblock,
  Stratum V1, version rolling, vardiff и распространение локального блока.

Наличие перечисленного означает реализацию и ограниченное тестовое покрытие,
а не доказательство всех крайних случаев.

## Консенсус и политика — разные критерии

Полная нода должна самостоятельно проверять блоки и выбирать допустимую цепь по
накопленной работе. Политики mempool/relay локальны: нода может не принимать для
relay транзакцию, которая допустима внутри блока. Поэтому копирование всех значений
Core не является условием валидности майнинга; разделение policy/consensus обязательно.
В этом аудите не установлен новый конкретный случай принятия consensus-invalid блока;
также не доказано отсутствие такого случая.

Core 31 перешёл от ancestor/descendant limits к cluster mempool и обновил RBF/отбор.
Основание сравнения: [release notes Core 31.0](https://bitcoincore.org/en/releases/31.0/).
Поведение P2P и лимиты сопоставлены с
[net_processing.cpp Core v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/net_processing.cpp):
его внутренняя порция исходящих getdata не является лимитом приёма таких сообщений.
Консенсусные и policy-пути следует сравнивать раздельно с
[validation.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp) и
[policy](https://github.com/bitcoin/bitcoin/tree/v31.1/src/policy).

## Критерии допуска к реальному майнингу

1. Закрыть P0 и P1 сетевой устойчивости; воспроизвести сценарии regression-тестами.
2. Выполнить mainnet replay с сопоставлением состояния Core и отдельные differential
   block/reorg/fuzz-тесты. Повторить проверки для целевой сети и версии Core.
3. Проверить аварийное восстановление, рост базы, нагрузку mempool и P2P,
   многочасовую работу с задержками, потерями соединений и сменой лучшей ветки.
4. Проверить конкретный ASIC, payout script, отмену устаревшей работы и задержку
   распространения блока на нескольких независимых пирах.

До этого разумный режим проекта — regtest и контролируемые эксперименты.
Кошелёк, pruning, txindex, BIP324 или публично открытый inbound-порт не являются
обязательными условиями консенсусно валидного solo-майнинга. Они не должны подменять
исправление перечисленных рисков валидации, синхронизации и relay.
