# Сроки загрузки заголовков: Core 32.1

Эталон — сохранённый `target/core-update-audit/core32-net-processing.cpp`
и нативный `bitcoin-32.1/bin/bitcoind.exe`.

В стандартной конфигурации начальный срок каждого пира вычисляется в микросекундах:

```
deadline = now_us + 900_000_000
           + trunc(1000 * (now_seconds - best_header_seconds) / target_spacing_seconds)
```

Масштабирование выполняется до деления, включая отрицательный возраст будущего
заголовка. Следующие ответы не продлевают срок. После достижения заголовка
строго новее `now - 24h` срок этого пира отключается окончательно.

Тайм-аут действует только строго после срока, при одном начавшем синхронизацию
пире и хотя бы одном другом предпочтительном пире. Обычное соединение
закрывается; NoBan сохраняется со сбросом состояния синхронизации. Неполученный
ответ не отмечается как успешно принятый.

Предпочтение: исходящий либо NoBan, не ADDR_FETCH, с NODE_NETWORK или
NODE_NETWORK_LIMITED. Учитываются готовые управляемые соединения; закрытие и
удаление очищают состояние. При отсутствии предпочтительных пиров либо блоков
в полёте разрешён запасной источник; старые заголовки начинают загружаться
одним пиром, свежие допускают несколько источников.

Автоматический supervisor запускается до ожидания заголовков. Начальный и live
пути имеют независимые задачи пиров, поэтому молчащий источник не блокирует
остальных. Общий dispatcher и ограничитель GETHEADERS сохраняются. Готовность
майнинга по-прежнему зависит от принятой цепи и обычных проверок актуальности.
Supervisor передаёт начальные запросы загрузчику, без собственной отправки
в обход начальной политики;
[проверка владения запросом](initial-recovery-owner-core32.md).
При первом запросе locator начинается с предшественника лучшего заголовка,
если он есть; [сценарии genesis, gate retry и продолжения](initial-locator-core32.md).
Chainwork-таймер supervisor ждёт фактического допуска начальной синхронизации,
а не только передачи запроса координатору;
[проверки deferred-пиров и границ 20/2 минут](chainwork-start-gate-core32.md).
Завершающая chainwork-проба от genesis использует пустой locator, в отличие
от начального запроса; [нативная проверка формы и границ](chainwork-null-locator-core32.md).

Стандартное значение header-response-timeout (120 секунд) выбирает политику
Core вместо прежнего пятисекундного live-предела. Явно заданные другие значения
сохраняют прежний режим пользовательского ограничения времени.

Проверки:

- HeadersSyncTimeoutPolicyTest: дробная часть формулы, строгие границы,
  альтернативы, NoBan, постоянное отключение срока после свежего заголовка.
- PreferredHeadersPeerTest: роли, сервисы, счётчики, откат резервирования.
- CoreHeaderTimingIntegrationTest: управляемые часы и независимое продвижение
  здорового пира при молчащем источнике.
- BitcoinCoreHeadersTimingWireTest: настоящий Core с mocktime, молчащим
  источником и исходящей альтернативой; оба варианта NoBan. До срока пир
  сохраняется; без альтернативы сохраняется и после срока; с альтернативой
  обычный отключается, NoBan начинает синхронизацию заново.

Оставшиеся границы: Core учитывает предпочтение уже после VERSION, Java —
после готовности handshake. Полный SendMessages scheduler, состояния импорта/
reindex и вся классификация ошибок блоков/транзакций этим изменением не закрыты.
Выбор источников заданий блоков при IBD теперь использует общее предпочтение;
availability GETHEADERS в block-policy refresh также используют общее состояние
допуска, locator и сроков;
[объединение и проверки block IBD](availability-headers-owner-core32.md).
В availability-пути внутренние ошибки не скрываются как неответивший пир;
[граница ошибок locator/транспорта](availability-failure-boundary-core32.md).
Это подтверждение перечисленных правил срока, а не полного совпадения всей
синхронизации.

Итоговая проверка 8 ноября: полный Bitcoin/RVN reactor — 5351 тест, 5339
успешных, 12 пропущенных, без ошибок; журнал
`target/core-update-audit/core32-header-timing-truc-full-build-complete.log`.
Рабочая IDEA GPU-нода PID 19404: RUNNING, height=headers=975028,
IBD=false, десять пиров (два block relay), принятые CUDA shares, один процесс.

Промежуточный пятисекундный failover-сбой впоследствии воспроизведён серией
переподключений и разобран в отладчике: тестовый пир ошибочно запрещал
повторный locator от genesis. [Исправление и регрессия](header-failover-fixture-core32.md).
Лимит теста не увеличивался, production-правила ради него не ослаблялись.
