## Что исправить первым

### Выполнено после аудита: бюджет объявлений транзакций

В `TransactionRequestScheduler` добавлены лимиты: 16384 хеша глобально,
2048 объявлений на пира, 4 источника на хеш, 128 активных запросов на пира
при общем пределе 1024. Ожидающие объявления живут 2 минуты; повторное inv
не обновляет срок. Активный запрос сохраняется до ответа/30-секундного timeout.
Квоты освобождаются после получения транзакции, notfound, timeout и удаления
неподходящего/отключённого источника при следующем вызове schedule (таймер 1 секунда,
при перегруженном worker возможна задержка). Переполнение отклоняет новые объявления.

Проверены поток 50000 объявлений, глобальное переполнение, TTL, лимит источников,
освобождение квот и прогресс второго пира при перегрузке первым. Это ограничивает
влияние одного пира. Добавлена ротация источников по одному запросу за ход;
порядок сохраняется между вызовами schedule, включая пополнение одного свободного

### 1. Ограничить накопление объявлений транзакций

`TransactionRequestScheduler.announced` безусловно добавляет новые хеши в `candidates`.
Лимит 1024 относится только к выполняющимся запросам. У ожидающего объявления нет
TTL, глобального/per-peer лимита или ограничения числа источников на хеш.
При непрерывном потоке уникальных inv от живого пира рост памяти не ограничен.
Ограничение входящей очереди NodeRelayService не ограничивает уже сохранённую карту.

Нужно: глобальный и per-peer budget, TTL ожидающих объявлений, предел источников,
fair scheduling и очистка при disconnect. Тесты: много последовательных inv,
несколько источников, истечение TTL, переполнение и сохранение прогресса честного пира.
Это подтверждено структурой кода; расход памяти под атакой в этом аудите не измерялся.

### 2. Убрать полный обход предков с горячего пути

Доработано после аудита: `BlockFailureResolver` использует LRU-кэш до 65536
результатов ancestry. Версия namespace статусов в общем RocksDbDatabase меняется
после успешных put/delete/write; разные экземпляры store видят одну версию.
Записи заголовков/UTXO не сбрасывают кэш. Отменённый batch не меняет версию.
Смена версии сбрасывает кэш, изменение во время обхода вызывает повтор проверки.
Предварительная проверка additionallyFailed имеет отдельный контекст кэша и не
смешивается с проверкой сохранённого состояния. Store без поддержки версии работает
без межвызовного кэширования. Индексы предполагаются неизменяемыми по хешу.

Регрессионный тест на 70000 последовательных индексов подтверждает 69999 чтений
родителя, включая вытеснение старых записей из кэша. Это проверка алгоритмической
стоимости, не измерение полной mainnet-синхронизации. Первый холодный обход и обход
после инвалидизации по-прежнему зависят от глубины цепи. `BlockFailureManager.findAll`
и индекс кандидатов по работе пока не переработаны; пункт 2 закрыт только частично.

Проверка: полный прогон `app/target/failure-cache-tests.log` — 3470 тестов,
3 skipped, 0 failures/errors, exit code 0; Core roundtrip выполнен (6.457 с).
После добавления двух дополнительных сценариев выполнен целевой прогон
`app/target/failure-cache-focused.log`: 6 BlockFailureResolverTest и 2
BlockFailureRecoveryTest, без failures/errors, exit code 0.

Исходное наблюдение аудита до этой доработки:

`BlockFailureResolver.isFailed` читает предков до genesis и создаёт visited-set.
Он вызывается при обработке headers и blocks. На цепи длиной H отдельная проверка
требует O(H), а последовательный проход истории даёт O(H²) обращений без кэширования.
`BlockFailureManager.markFailed` дополнительно загружает все индексы и проверяет
предков каждого кандидата. Это алгоритмический вывод, не результат mainnet-бенчмарка.

Нужно: кэш/сохранённый статус валидности ancestry, корректная инвалидизация потомков,
индекс кандидатов по работе и потоковый доступ вместо findAll. Также оптимизировать
`NodeValidationService.headers/findBlock`, которые проходят активных предков.
Сохранить проверки отказа/перезапуска; добавить замер числа чтений на длинной цепи.

### 3. Завершить ограничения P2P-ресурсов и приоритет блока

- Очередь PeerOutbound ограничивает число задач, но не удерживаемые байты/векторы.
  Одна задача getdata хранит до 50000 элементов, очередь — до 64 таких задач на пира.
  Нужны per-peer и общий бюджеты памяти, лимиты обработки и пропускной способности.
- `serveData` обрабатывает весь getdata в одной FIFO-задаче. Свежий inv/headers блока
  может ждать за выдачей истории тому же пиру. Разбить обслуживание на порции и
  отдельно приоритизировать свежие блоки; избежать голодания обычных запросов.
- `PeerLivenessService.checkPeers` синхронно вызывает `sendPingIfDue`, который пишет
  непосредственно в connection под pingLock. Один заблокированный send может задержать
  проверки остальных пиров. Перевести heartbeat и остальные прямые ответы в общий
  bounded writer с deadline; тестировать остановку сервиса при заблокированной записи.
- В `PeerAddressProtocol` нет per-peer token bucket для addr/addrv2. Обработка идёт
  на reader. Нужны rate limiting, бюджет CPU/очереди и критерии disconnect/discouragement.
  Ограничение getaddr одним ответом уже существует и не заменяет эти меры.

### 4. Доказать правильность валидации и восстановления

Основные механизмы консенсуса реализованы, но тесты не доказывают полную эквивалентность.
Нужно провести полную историческую синхронизацию mainnet с закреплённой версией Core,
сопоставлением chainwork/tip и UTXO digest на контрольных высотах; проверить переходы
активаций, исторические исключения и ветки вне активной истории.

Отдельные обязательные сценарии: невалидная ветка большей работы, глубокий reorg,
ошибка скрипта, ошибочное witness-тело при том же заголовке, сбой хранения. Повреждённое
сообщение или I/O-ошибка не должны навсегда помечать валидный header как failed.
Проверить kill/restart между записью блоков, UTXO, undo и tip; повторная обработка
после восстановления должна давать то же состояние, что Core.

### 5. Зафиксировать цель совместимости политик

`MempoolLimits` остаётся на ancestor/descendant 25/25 и family 101000 vB;
`MempoolGraphPolicy` сохраняет прежний подход. Core 31 использует cluster mempool,
cluster limits и обновлённый RBF/порядок отбора. Полное совпадение политик требует
отдельного переноса и differential-тестов, а не простой замены константы 25 на 64.
Источник: [официальные release notes Core 31.0](https://bitcoincore.org/en/releases/31.0/).

Политика mempool/relay локальна. Различие с Core само по себе не делает блок
consensus-invalid. Для валидного майнинга критично не применять ограничения policy
как дополнительные правила при проверке чужих блоков.

### 6. Проверить mining и relay в условиях эксплуатации

Сценарий трёх узлов: Core A → Java → Core B, включая входящий блок, reorg, отставший
пир и reconnect. Проверять фактическое принятие блока получателем, не только вызов
mock Peer.send. Измерять задержку от принятия/нахождения блока до его передачи.
Следующий этап — длительная работа конкретного ASIC с payout script владельца,
version rolling/vardiff, сменой tip, потерями сети и контролем stale/rejected shares.

## Дополнительная функциональность

Для эффективного mainnet relay добавить BIP130 sendheaders, BIP152 compact blocks,
feefilter, сетевой package relay. Проверить fallback для обычных блоков и старых пиров.
Для эксплуатации нужны метрики пиров/очередей/chain lag/шаблонов, диагностика причин
отклонения блока, инструменты восстановления базы и мониторинг свободного диска.

Кошелёк, полный RPC Core, txindex, pruning, BIP324 и публичный входящий порт сами по
себе не обязательны для консенсусно валидного solo-майнинга. Их наличие не заменит
проверок валидации, восстановления, актуальности работы и публикации блока.
